# 人像分割云函数 · 部署说明

这个云函数负责「判断哪里是人、哪里是背景」，只回传遮罩（灰度 PNG），
合成仍然在小程序本机做。处理完立刻删除云存储里的临时文件。

---

## 一、为什么用云函数而不是自己买服务器

- 不用域名、不用备案、不用运维
- 有免费额度，早期基本不花钱
- 换模型不用发版，改云端就行

**不需要 GPU。** MODNet / U2Net-small 这类模型在 2 核 CPU 上跑一张 720×960 大约 200–600ms。

---

## 二、部署步骤

### 1. 开通云开发

微信开发者工具 → 顶部「云开发」→ 开通，记下**环境 ID**（形如 `prod-1a2b3c`）。

### 2. 把模型文件放进来

把量化后的 ONNX 模型放到：

```
cloudfunctions/segment/model/portrait.onnx
```

推荐这几个（都已在大规模人像数据上训练好，不用自己训）：

| 模型 | 体积 | 特点 |
|---|---|---|
| MODNet（量化版） | 2–3 MB | 边缘质量好，人像首选 |
| U2Net-portrait（small） | 4–5 MB | 更稳，但慢一些 |
| RMBG-1.4（onnx） | 40 MB+ | 效果最好，云函数体积吃紧 |

**输入必须是 320×320、RGB、NCHW、float32、0~1 归一化**，输出是 [1,1,320,320] 的概率图。
你下的模型如果输入尺寸或归一化方式不一样，改 `index.js` 里的 `INPUT_SIZE` 和归一化那两行。

### 3. 安装依赖

**不要在自己电脑上 `npm install`。** onnxruntime-node 和 sharp 都带原生二进制，
在 Mac 上装的是 darwin 版，上传到云函数（Linux）会直接报错。

正确做法：右键云函数目录 → **「上传并部署：云端安装依赖」**。
云端会按 Linux 环境装好，这也是唯一省事的办法。

### 4. 调大超时和内存

云函数默认超时 3 秒、内存 256MB，冷启动加载模型会超。

在云开发控制台 → 云函数 → segment → 配置：

- **超时时间**：改成 **20 秒**
- **内存**：改成 **512MB**（sharp 解码 + 模型推理够用）

不调这两项，第一次调用几乎必然超时。

---

## 三、会踩的坑（按概率排序）

**① 忘了「云端安装依赖」，直接上传本地 node_modules**
→ 报 `invalid ELF header` 或 `cannot find module`。删掉本地 node_modules 重新云端安装。

**② 模型路径不对**
→ `模型文件缺失: /var/user/model/portrait.onnx`。确认文件真的在 `cloudfunctions/segment/model/` 下，
而且上传时没被 `.gitignore` 或打包规则排除。

**③ 算子不支持**
→ `session.create` 失败，报 `Unsupported operator`。换一个算子更保守的模型，
或者用 onnx-simplifier 先做一遍图优化。

**④ 冷启动慢**
→ 第一次调用可能 3–5 秒（加载模型）。可以在小程序端做「预热」：
进入编辑页就先发一个空调用把实例拉起来。

**⑤ 输出形状不对**
→ 有的模型输出 `[1,1,H,W]`，有的 `[1,H,W]`。如果取到的长度不对，
在 `index.js` 里按实际形状取通道。

## 五、隐私口径必须同步改

上了这个云函数之后，「照片不出手机」这句话就不成立了。对外必须改成：

> 照片仅用于本次处理，处理完立即从内存释放，不在服务器保存。

《用户隐私保护指引》里也要补一条：会传输到服务器处理，但不存储。
**这一步不能省，也不能含糊——被举报一次就是下架。**

## 六、实测记录（2026-10-22，环境 workbuddy-d7gdllq7e3ca333ec）

模型：`Xenova/modnet` 的 `onnx/model_quantized.onnx`，**6.3MB**
输入：动态尺寸，实际用 **320×320**（512 会爆 256MB 内存）
归一化：`px / 127.5 - 1` → [-1, 1]（来源 `preprocessor_config.json`，mean=0.5 std=0.5）
输出：`[1,1,H,W]` float32，0~1 概率图

跑通过程中踩了三个坑，都已解决：

| 现象 | 原因 | 解决 |
|---|---|---|
| `145 code exit unexpected`，Duration 0 / MemUsage 0 | `sharp` 是原生模块，云端装依赖失败，函数启动即崩 | **去掉 sharp**，改用纯 JS 的 `jpeg-js` + 自己写双线性缩放和 PNG 编码 |
| `Task memory exceeded 256 MB` | 512×512 推理 + onnxruntime 运行时超 256MB | 输入降到 **320×320** |
| `mask 全黑，检查归一化` | 归一化区间用错（写成 [0,1]）会大面积输出 0 | 改回 `px/127.5 - 1` |

当前表现（320 输入、冷启动）：**Duration 2237ms，MemUsage 118MB**，稳定在 256MB 以内。
热启动会明显更快。真机上的实际耗时取决于网络 + 冷热状态。

> 注意：遮罩全黑时函数返回 `ok:false` 而不是假装成功，客户端应当据此降级到本地颜色算法。
